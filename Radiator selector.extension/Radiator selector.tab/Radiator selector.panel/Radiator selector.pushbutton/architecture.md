# Архитектура Radiator Selector

> Документ описывает фактическое состояние ветки `main` репозитория
> `KOT-B-CMETAHKE/Radiator-Selector` на момент подготовки версии 1.0.
> Отдельно отмечены целевые изменения, которые ещё не реализованы в коде.

## Назначение плагина

`Radiator Selector` — расширение для pyRevit, автоматизирующее подбор отопительного прибора для помещений модели Revit при заранее рассчитанной требуемой тепловой мощности.

Плагин:

- собирает помещения и окна из модели Revit;
- ограничивает обработку фазой активного вида;
- проверяет исходные данные модели;
- загружает каталог радиаторов из файла `radiators.csv`;
- подбирает радиатор по тепловой мощности и допустимой длине;
- формирует текстовый отчёт по модели, помещениям и проблемным окнам.

Цель проекта — сократить объём ручной работы при подборе отопительных приборов и централизовать проверку исходных данных.

## Область ответственности

Версия 1.0 работает только в режиме чтения модели.

Плагин:

- не изменяет параметры элементов Revit;
- не создаёт новые типы семейств;
- не размещает радиаторы в модели;
- не рассчитывает теплопотери помещений;
- не исправляет некорректные исходные данные автоматически.

Требуемая тепловая мощность должна быть рассчитана заранее и записана в параметр помещения `Требуемая тепловая мощность`.

## Общий поток данных

```text
Revit API
   │
   ▼
script.py
   │  ModelInput
   │  ProblematicWindows
   ▼
handler.py
   │
   ├── catalog.py ──► CatalogLoaderResult
   │
   └── selector.py ─► SelectRadiatorResult
   │
   ▼
HandlerResult
   │
   ├──────────────────────────┐
   │                          │
   ▼                          ▼
HandlerResult          ProblematicWindows
   └──────────────┬───────────┘
                  ▼
             displayer.py
                  │
                  ▼
          текстовый отчёт pyRevit
```

Последовательность выполнения:

1. `script.py` получает документ Revit и фазу активного вида.
2. Из документа собираются все помещения и окна.
3. Помещения и окна фильтруются по активной фазе.
4. Для помещений проверяются геометрия и параметр требуемой мощности.
5. Для окон проверяются ширина и связь с помещением.
6. Связанные окна добавляются в соответствующие `RoomInput`.
7. Окна без определённого обрабатываемого помещения попадают в `ProblematicWindows`.
8. `handler.py` загружает каталог через `catalog.py`.
9. При успешной загрузке каталога каждое помещение обрабатывается отдельно.
10. Для подходящего помещения вызывается `selector.py`.
11. `handler.py` возвращает `HandlerResult`.
12. `displayer.py` получает `HandlerResult` и `ProblematicWindows`, после чего формирует отчёт.

## Ответственность модулей

### `script.py`

Единственный модуль, непосредственно работающий с Revit API.

Отвечает за:

- получение активного документа;
- получение фазы активного вида;
- сбор помещений и окон;
- фильтрацию элементов по фазе;
- преобразование внутренних единиц Revit в миллиметры и ватты;
- проверку исходных данных модели;
- определение связи окна с помещением через `FromRoom` и `ToRoom`;
- формирование `ModelInput` и `ProblematicWindows`;
- запуск `handler.process_model()`;
- передачу результатов в `displayer.run()`;
- перехват непредвиденных исключений верхнего уровня.

Внутренние функции:

- `resolve_window_placement()` — определяет расположение окна относительно помещений;
- `resolve_window_width()` — получает ширину окна и проверяет параметр;
- `resolve_required_heat_power()` — получает требуемую тепловую мощность помещения.

Все проверки, зависящие от Revit API, должны оставаться в `script.py`. Остальные модули не должны получать объекты Revit.

### `handler.py`

Координирует расчётную часть плагина.

Отвечает за:

- загрузку каталога;
- блокировку обработки при критической ошибке каталога;
- обработку каждого помещения независимо от остальных;
- объединение проблем помещения и связанных с ним окон;
- проверку количества окон;
- вызов `selector.select_radiator()`;
- формирование `RoomResult`;
- формирование общего `HandlerResult`;
- определение статуса помещений и текущего общего статуса обработчика.

`handler.py` не должен обращаться к Revit API и не должен заниматься форматированием пользовательского отчёта.

### `catalog.py`

Отвечает за чтение и первичную проверку `radiators.csv`.

Фактическое поведение:

- путь строится относительно расположения `catalog.py`;
- проверяется существование файла;
- используется разделитель `;`;
- заголовки поддерживаются на русском и английском языках;
- запятая в числах может заменяться на точку;
- некорректные строки пропускаются;
- при частичной загрузке возвращается предупреждение;
- при отсутствии корректных строк загрузка считается неуспешной.

`catalog.py` не выбирает радиатор и не зависит от Revit API.

### `selector.py`

Содержит чистую логику подбора радиатора для одного помещения.

Входные данные:

- ширина окна в миллиметрах;
- требуемая тепловая мощность в ваттах;
- загруженный каталог радиаторов.

Условия подбора:

- длина радиатора — от 50 до 85% ширины окна;
- минимальный запас мощности — 10%;
- желательный запас — от 10 до 15% включительно;
- допустимый запас — более 15%, но не более 20%;
- из подходящих приборов выбирается прибор с минимальной теплоотдачей.

Если прибор найден только в допустимом диапазоне запаса, результат содержит предупреждение `EXCEEDED_DESIRABLE_POWER_RESERVE`.

### `displayer.py`

Отвечает за текстовый вывод результатов в pyRevit.

В текущей реализации:

- показывает общий исход обработки;
- считает помещения по статусам `OK`, `WARNING`, `ERROR`;
- показывает результаты каждого помещения;
- повторно рассчитывает фактический запас мощности;
- выводит коды ошибок и предупреждений;
- отдельно выводит проблемные окна.

Целевое правило: `displayer.py` должен только отображать уже подготовленные данные и не должен повторно рассчитывать статусы, статистику или инженерные значения.

### `models.py`

Содержит общие модели и константы, используемые всеми модулями.

В текущей реализации содержит:

- статусы `OK`, `WARNING`, `ERROR`;
- класс `Issue`;
- класс `IssueCode`;
- класс `Stage`;
- класс `Severity`;
- класс `IssueContext`;
- функцию `get_status_from_issues()`;
- функцию `get_status_from_statuses()`.

`models.py` не должен импортировать Revit API и не должен содержать бизнес-логику подбора.

## Контракты данных

### Общие понятия

В результатах используются три независимых понятия.

#### `outcome`

Показывает, чем закончилась конкретная операция:

- была ли модель обработана;
- было ли помещение обработано, пропущено или завершилось ошибкой;
- загрузился ли каталог;
- был ли выбран радиатор.

`outcome` описывает ход операции, но не заменяет `status`.

#### `status`

Показывает максимальную критичность найденных проблем:

- `OK` — проблем нет;
- `WARNING` — есть хотя бы одно предупреждение, но нет ошибок;
- `ERROR` — есть хотя бы одна ошибка.

#### `issues`

Содержит конкретные причины предупреждений и ошибок.

Ожидаемые ситуации должны передаваться через `Issue`, а не через исключения Python.

### `Issue`

В актуальном коде ошибка или предупреждение хранится не в словаре, а в экземпляре класса:

```python
Issue(
    code=ISSUE_CODE,
    stage=ISSUE_STAGE,
    severity=Severity.WARNING,  # или Severity.ERROR
    context=IssueContext(...),  # optional
)
```

Поля:

- `code` — машинный код проблемы;
- `stage` — этап, на котором проблема обнаружена;
- `severity` — критичность;
- `context` — дополнительные сведения.

### `IssueContext`

Поддерживаемые поля текущей реализации:

```python
IssueContext(
    id=None,
    actual_power_reserve_pct=None,
    radiators_load_success_pct=None,
    unknown_error=None,
)
```

Назначение:

- `id` — ID элемента Revit;
- `actual_power_reserve_pct` — фактический запас мощности;
- `radiators_load_success_pct` — доля корректно загруженных строк каталога;
- `unknown_error` — исходное исключение для диагностики.

### Статусы

```python
STATUS_OK = "OK"
STATUS_WARNING = "WARNING"
STATUS_ERROR = "ERROR"
```

Приоритет:

```text
OK < WARNING < ERROR
```


Сюда попадают окна, которые:

- находятся между двумя помещениями;
- не имеют связанного помещения;
- связаны с помещением, не вошедшим в `ModelInput`.

В текущей версии `ProblematicWindows` не входит в `ModelInput` и передаётся в `displayer.py` отдельно.

## Контракты `handler.py`

### `RoomResult`

```python
{
    "outcome": (
        "ROOM_PROCESS_SUCCESS"
        | "ROOM_PROCESS_SKIPPED"
        | "ROOM_PROCESS_FAILED"
    ),
    "status": "OK" | "WARNING" | "ERROR",
    "name": str | None,
    "number": str | None,
    "required_heat_power_w": float | None,
    "no_windows": bool,
    "radiator": Radiator | None,
    "issues": [Issue],
}
```

Правила формирования:

1. В `issues` копируются проблемы самого помещения.
2. Затем в него добавляются проблемы всех связанных окон.
3. Наличие ошибки исходных данных блокирует подбор только этого помещения.
4. Отсутствие окон приводит к `ROOM_PROCESS_SKIPPED` и предупреждению.
5. Более одного окна приводит к `ROOM_PROCESS_FAILED`.
6. При одном корректном окне выполняется подбор радиатора.
7. `status` вычисляется по полному списку `issues` помещения.

### `HandlerResult`

```python
{
    "outcome": "MODEL_PROCESS_SUCCESS" | "MODEL_PROCESS_FAILED",
    "status": "OK" | "WARNING" | "ERROR",
    "rooms": {
        room_id: RoomResult,
    },
    "issues": [Issue],
}
```

В текущей реализации:

- `issues` содержит только проблемы загрузки каталога;
- критическая ошибка каталога приводит к `MODEL_PROCESS_FAILED`;
- `MODEL_PROCESS_SUCCESS` означает, что каталог загрузился и цикл обработки помещений был выполнен;
- ошибки отдельных помещений не меняют `outcome` модели на `MODEL_PROCESS_FAILED`;
- итоговый `status` после обработки определяется по статусам помещений.

## Контракт `displayer.py`

```python
displayer.run(problematic_windows, handler_result)
```

Входные данные:

- `ProblematicWindows`;
- `HandlerResult`.

`displayer.py` не возвращает расчётный результат. Его побочный эффект — печать отчёта.

## Система ошибок и результатов

### Жизненный цикл проблемы помещения

```text
script.py обнаруживает проблему модели
              │
              ▼
Issue записывается в RoomInput или WindowInput
              │
              ▼
handler.py переносит проблемы в RoomResult
              │
              ▼
status помещения рассчитывается по issues
              │
              ▼
displayer.py выводит код проблемы
```

### Жизненный цикл проблемы каталога

```text
catalog.py обнаруживает проблему
              │
              ▼
Issue записывается в CatalogLoaderResult
              │
              ▼
handler.py переносит его в HandlerResult.issues
              │
              ├── ERROR: обработка блокируется
              │
              └── WARNING: обработка помещений продолжается
```

### Локальные ошибки

Локальная ошибка относится к конкретному помещению или окну и не должна останавливать обработку остальных помещений.

Примеры:

- отсутствует параметр мощности;
- некорректна ширина окна;
- помещение имеет несколько окон;
- подходящий радиатор не найден.

### Глобальные ошибки

Глобальная ошибка не позволяет выполнить подбор для всей модели.

В текущей реализации к глобальным относятся ошибки загрузки каталога:

- файл отсутствует;
- отсутствует обязательный заголовок;
- все строки каталога некорректны;
- при загрузке произошло непредвиденное исключение.

### Проблемные окна

Проблемы окон, не связанных с обрабатываемым помещением, хранятся отдельно от `HandlerResult`.

Они выводятся в отчёте, но в текущей реализации не участвуют в формировании `HandlerResult.status`.

## Основные архитектурные правила

1. **Revit API изолирован в `script.py`.** Расчётные модули получают только стандартные Python-структуры и объекты `Issue`.
2. **Ожидаемые ошибки представлены данными.** Проверяемая проблема создаёт `Issue`, а не выбрасывает исключение.
3. **Непредвиденные исключения не скрываются полностью.** Они перехватываются на границе соответствующего уровня и сохраняются в диагностическом контексте либо выводятся верхнеуровневым обработчиком.
4. **Одно проблемное помещение не останавливает обработку модели.** Блокирующей для всей модели считается только глобальная ошибка.
5. **`outcome`, `status` и `issues` имеют разные назначения.** Они не должны заменять друг друга.
6. **Статус вычисляется из проблем.** `ERROR` имеет приоритет над `WARNING`, `WARNING` — над `OK`.
7. **Модуль отображения не должен принимать инженерные решения.** Расчёты должны выполняться до передачи результата в `displayer.py`.
8. **Контракты результата стабильны.** Модуль должен возвращать словарь установленной структуры при любом штатно обработанном исходе.
9. **Коды и константы централизуются.** Новые `IssueCode`, `Stage`, `Severity`, статусы и outcomes не должны размножаться строковыми литералами по модулям.
10. **Единицы явно указаны в названиях полей.** Для нормализованных данных используются суффиксы `_mm`, `_w`, `_pct`.

## Известные несоответствия текущей реализации

Ниже перечислены не целевые правила, а фактический технический долг текущего `main`.

### Общий статус не охватывает все источники проблем

После успешной загрузки каталога `HandlerResult.status` вычисляется только по помещениям. Поэтому:

- предупреждение о частично повреждённом каталоге может не попасть в итоговый статус;
- проблемы из `ProblematicWindows` не влияют на итоговый статус модели.

### `get_status_from_statuses()` не соответствует своему входному контракту

Функция получает строки статусов, но обращается к ним через `status.severity`. Перед использованием функцию необходимо исправить либо заменить агрегатором с явным приоритетом статусов.

### `displayer.py` повторно обрабатывает результат

Сейчас модуль отображения:

- повторно вычисляет статус помещения;
- самостоятельно считает статистику;
- повторно рассчитывает запас мощности;
- вычисляет статус проблемных окон, но не использует его.

Целевое состояние — передавать в отображение полностью подготовленный результат и сводку.

### Outcome модели сформулирован неоднозначно

`MODEL_PROCESS_SUCCESS` устанавливается после успешной загрузки каталога, даже если некоторые помещения завершились с `ERROR`.

Для дальнейшего развития предпочтительнее разделить:

- факт завершения процесса;
- критичность результата.

Например:

```text
outcome = MODEL_PROCESS_COMPLETED
status = ERROR
```

### Строковые значения outcomes не централизованы

Outcomes каталога, модели, помещения и подбора записаны строками непосредственно в модулях. Это создаёт риск опечаток.

### Сообщения пользователю содержат только коды

`displayer.py` выводит `Issue.code`, но не переводит его в понятное описание. Для релиза нужен централизованный словарь пользовательских сообщений.

## Целевая схема результата модели

Этот раздел описывает планируемое развитие и не соответствует текущему контракту `handler.process_model()`.

Целевой результат:

```python
{
    "outcome": "MODEL_PROCESS_COMPLETED" | "MODEL_PROCESS_BLOCKED",
    "status": "OK" | "WARNING" | "ERROR",
    "issues": [Issue],                # только общие проблемы
    "rooms": {
        room_id: RoomResult,
    },
    "problematic_windows": {
        window_id: WindowResult,
    },
    "summary": {
        "rooms_total": int,
        "rooms_selected": int,
        "rooms_skipped": int,
        "rooms_failed": int,
        "rooms_ok": int,
        "rooms_warning": int,
        "rooms_error": int,
        "problematic_windows": int,
    },
}
```

Статус модели должен агрегироваться из:

1. общих проблем модели и каталога;
2. статусов всех помещений;
3. статусов проблемных окон.

Сами дочерние проблемы не должны копироваться в общий список `issues`.

## Ограничения текущей версии

- обрабатываются только помещения активной фазы;
- окна учитываются только в состояниях `New` и `Existing` для активной фазы;
- связанные модели Revit не обрабатываются;
- поддерживается только одно связанное окно на помещение;
- помещение без окон пропускается;
- окно между двумя помещениями считается внутренним и не привязывается к одному из них;
- балконы и лоджии отдельно не распознаются;
- параметр мощности должен называться `Требуемая тепловая мощность`;
- ширина окна считывается из встроенного параметра типа;
- каталог выбирается только из файла `radiators.csv` рядом со скриптом;
- пользовательский выбор файла каталога отсутствует;
- результаты не записываются в модель;
- встроенный каталог должен рассматриваться как демонстрационный, если его характеристики не подтверждены производителем;
- совместимость рассчитана на текущую конфигурацию pyRevit/IronPython, использующую `.decode()` при чтении CSV.

## Критерии готовности версии 1.0

Перед выпуском версии 1.0 необходимо:

- привести итоговый статус в соответствие со всеми источниками проблем;

- добавить человекочитаемые сообщения для кодов проблем;
- обеспечить контролируемый вывод непредвиденного исключения;
- проверить отсутствие каталога и повреждённый CSV;
- проверить уникальность артикулов каталога;
- явно обозначить демонстрационный характер встроенных данных;
- актуализировать `README.md`;
- удалить служебные файлы и папки из публичной истории;
- выполнить ручные тесты основных успешных и ошибочных сценариев.
